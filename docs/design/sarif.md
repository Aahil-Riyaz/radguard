# SARIF output

`radguard scan PATHS --format sarif --output radguard.sarif` writes a [SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/errata01/os/sarif-v2.1.0-errata01-os-complete.html) log, the format GitHub code scanning, Azure DevOps, VS Code's SARIF viewer and most security dashboards read. Code: [`src/radguard/sarif.py`](../../src/radguard/sarif.py). Sample: [`docs/sample-report.sarif`](../sample-report.sarif), RadGuard's scan of its own examples, regenerated by the tests.

SARIF was designed for source-code analysers. RadGuard reports on binary files built by an attacker, and almost every design decision below comes from that mismatch. Each one cites the spec (section numbers refer to SARIF 2.1.0 Errata 01), GitHub's documentation or behaviour, or what other scanners got wrong.

## Mapping

| RadGuard | SARIF |
|---|---|
| Rule catalog ([`rules.py`](../../src/radguard/rules.py), [reference](../rules.md)) | `tool.driver.rules`: id, PascalCase name, descriptions, advice as `help`, `helpUri` to the rule's section, tags, precision, `security-severity`, CWE `relationships` |
| Finding | `result`: `ruleId`, `level`, message, one location, fingerprints, RadGuard's severity in `properties` |
| Byte offset | `region.byteOffset`; no region when a finding is about the whole file |
| File with findings | `run.artifacts`: length, SHA-256 of the bytes examined, `application/dicom`, role `analysisTarget` |
| Path not examined (error) | `toolExecutionNotifications`, level `error`, and `executionSuccessful: false` |
| Path deliberately skipped (note) | notification, level `note` |
| Exit status | `invocations[0].exitCode` |
| CWE | `run.taxonomies` (CWE), referenced from each rule |

## Decisions

### Locations are binary regions

SARIF 3.30.1: "For regions in binary artifacts, a region object SHALL define a binary region and SHALL NOT define a text region." A DICOM file has no lines, so a result carries `region.byteOffset` and never `startLine`. Container scanners such as Trivy and Grype write a fake `startLine: 1` instead; besides breaking the spec, that makes GitHub's upload action fingerprint the result by hashing the file's first "line", which for a PE/DICOM polyglot is the attacker's preamble.

GitHub's documentation marks `startLine` as required, but GitHub's own CodeQL omits the region for non-text files, the advice in the upload action's issue tracker is to leave line information out for binary files ([codeql-action#754](https://github.com/github/codeql-action/issues/754)), and osv-scanner uploads region-less results every day. The CI job below uploads byte-offset results on every push, so if GitHub ever rejects them the build fails.

Findings carry a start offset, not an extent, so regions have no `byteLength`. Per 3.30.12 such a region is the point just before that byte: where the finding starts. A finding about the whole file gets the region `{byteOffset: 0, byteLength: <file size>}` rather than no region: the spec reads an absent region as the whole file anyway, but Microsoft's validator (SARIF2017) asks for it to be explicit, and being explicit costs nothing.

The offset is also written into the message ("At byte 0x418e of the file"). SARIF 3.27.11 asks for the location in the message, and GitHub shows the file of a binary region but not the offset.

**An offset is only a region if it counts bytes of the file.** A deflated file (transfer syntax 1.2.840.10008.1.2.1.99) is analysed after decompression, and a payload found in the decompressed dataset has an offset into that dataset, which can lie far beyond the end of the file. Before SARIF made this question unavoidable, findings did not record which kind of offset they carried, so the JSON report was ambiguous for deflated files. Every finding now has a `domain` (`file` or `inflated`); an inflated offset is reported on the file as a whole, and the offset and domain go in the message and the result's properties. The test suite checks every finding any test produces: its offset must lie inside the bytes its domain counts.

### RadGuard supplies the fingerprints

GitHub tracks an alert across runs only by `partialFingerprints.primaryLocationLineHash`, and the upload action computes that only for results with a `startLine` (`fingerprints.ts`: "Locations without a line number are unlikely to be source files"). Without our own, every run would open duplicate alerts. Each result therefore carries `primaryLocationLineHash` and the same value under the spec-style versioned key `radguard/v1`:

- input: the check id, the artifact URI and the offset, NUL-separated (fields cannot contain NUL, so two different inputs cannot collide by concatenation, a flaw in Grype's hash);
- the URI rather than the path as typed, so `examples/a.dcm` and `/home/ci/repo/examples/a.dcm` are the same alert;
- not the message (it embeds attacker text and wording changes), not the severity, not the file's content hash (Trivy's maintainers rejected content hashing as unstable);
- `hash:n`, numbering repeated findings at one place the way CodeQL does, so they stay separate alerts.

### Severity: a sub-rule when a finding differs from its rule

GitHub displays an alert's severity from its rule's `security-severity`, "in preference to" the result's `level`, and offers no per-result override. Eleven RadGuard rules legitimately vary: `values.embedded-file` is critical for an executable and low for a vendor PDF in a private tag. Prior art takes the rule from the first finding (Checkov), the last (Trivy) or the worst (osv-scanner); with any of these a hospital archive full of routine vendor XML shows up as hundreds of critical alerts, which trains people to ignore the tool.

So a finding at its rule's usual severity is reported under the rule, and one at a different severity under a sub-rule `<rule>/<severity>` (for example `values.embedded-file/low`), using the same `/` hierarchy as CodeQL's rule ids. The sub-rule has the parent's text and help link and its own level and score. The trade-off is that a finding whose severity changes would open as a new alert. That is acceptable here because the fingerprint includes the byte offset, so any change to a file large enough to change a severity already produces new alerts. Sub-rules appear in the log only when used; the full catalog is always present. Microsoft's validator notes that a non-normative note in the spec (3.49.3) expects sub-rules to share their parent's metadata; here the separate metadata is the point, since it is the only way to give GitHub a different severity, and GitHub's own CodeQL uses `/` in rule ids that carry their own metadata.

Scores sit inside GitHub's bands, never on a boundary ("over 9.0 is critical"): critical 9.5, high 8.0, medium 5.5, low 2.0, as strings (a non-numeric value fails the whole upload). Levels: critical and high are `error`, medium `warning`, low and info `note`.

### Attacker-controlled text is inert

File names and strings inside DICOM files (vendor names, MIME types) reach messages. SARIF viewers render `[text](target)` in a message as a link (3.11.6), GitHub may render messages as Markdown, and the alert title is shown to anyone who can read the repository's pull requests. `message_text` therefore:

- removes control, bidirectional and invisible characters (`output.safe`, the same sanitiser as the terminal output);
- backslash-escapes `\`, `[`, `]`, `<` and `>`, the backslash first so an attacker's backslash cannot cancel one of ours;
- also escapes a `(` that follows `]`: Microsoft's SARIF viewer matches links with a regular expression that ignores escapes, so `\[x\](https://evil)` would still have been a link there;
- doubles `{` and `}`, which are argument placeholders in every SARIF message (3.11.5);
- caps the text at 4,096 characters, and puts the tool-written title first, since GitHub shows only the first sentence when space is short.

A property test checks, for arbitrary input, that the result contains no link for either kind of renderer and that undoing the escapes gives back exactly the sanitised text: nothing is lost, only neutralised.

### Paths become percent-encoded URIs

`artifactLocation.uri` must be a valid RFC 3986 reference, and GitHub rejects the whole upload for one invalid URI (it has rejected names containing `:`). Trivy's writer crashes outright on a file named `100%.tf`. RadGuard encodes the name's bytes, keeping only unreserved characters and `/`:

- `:` is always encoded, so a file named `javascript:alert(1)` cannot become a URI with a scheme;
- the bytes are the name as the file system stores it: on POSIX, names that are not UTF-8 reach Python as surrogate escapes and are turned back into their original bytes (`x%FFy.dcm`); on Windows, an unpaired UTF-16 surrogate is kept with surrogatepass (`x%ED%B3%BFy.dcm`);
- paths under the directory RadGuard was run from are relative to `%SRCROOT%`; anything else, including paths that leave it through `..` or another drive, is an absolute `file:` URI (UNC shares and `\\?\` paths included). Relative references never start with `/`.

Property tests generate names full of URI delimiters and surrogates and check that the URI decodes back to exactly the original bytes.

### No absolute path of the scanning machine

`originalUriBaseIds` describes `%SRCROOT%` without its absolute URI, which SARIF 3.14.14 allows "to avoid revealing sensitive information". An absolute path names the analyst's account, DICOM directory names often carry patient identifiers, and GitHub ignores the field anyway. The log is also reproducible across machines as a result. The working directory, command line, environment and machine name are not recorded either.

### Completeness is part of the log

A scan that could not read everything must never look clean (exit status 3). In SARIF the same fact is `executionSuccessful: false`, and each path that was not examined is an `error` notification with its location; 3.20.21 says a consumer then "SHALL NOT assume that a failed run contains a complete set of analysis results". Deliberately skipped paths are `note` notifications.

A Git LFS pointer is an error too. A repository that stores DICOM files with Git LFS, checked out in CI without `lfs: true`, contains small text files in place of the images; skipping them as "not DICOM" would pass a scan that never saw a single image.

### Limits fail loud

GitHub rejects a run with more than 25,000 results. RadGuard keeps the 25,000 most severe (findings are already ordered by severity), reports the omission as a `warning` notification and in `properties.resultsOmitted`, and leaves the JSON report complete. Other limits are far away and checked in tests: at most 5 tags per rule (GitHub reads 10), descriptions under 1,024 characters, one location per result, one run per log.

### CWE as a taxonomy, and as tags

The spec's way to classify rules is a taxonomy (3.19.3, 3.49.15): the log carries a CWE taxonomy with the eleven CWEs RadGuard uses, and each rule declares a `relevant` relationship to its CWEs. GitHub ignores taxonomies but understands `external/cwe/cwe-N` tags, so both are written.

## Validation

- **Schema:** every SARIF document the tests produce is validated against the official OASIS schema ([`tests/schemas/sarif-schema-2.1.0.json`](../../tests/schemas/sarif-schema-2.1.0.json), pinned by SHA-256), with URI and date-time formats checked. A test first proves the validator rejects an invalid log, so the check cannot pass vacuously.
- **GitHub:** the `code-scanning` CI job scans `examples/` and uploads the log with `github/codeql-action/upload-sarif`. The action stops waiting after about two and a half minutes and then passes even if GitHub later rejects the file, so the next step asks GitHub's API for the upload's processing status and fails the job unless it is `complete`.
- **Microsoft's SARIF Multitool:** the same CI job runs `sarif-multitool validate` with its SARIF and GitHub rule sets over the real scan and over a generated log ([`scripts/sarif_edge_cases.py`](../../scripts/sarif_edge_cases.py)) that exercises every branch of the writer: an incomplete scan, a skipped path, a severity sub-rule, an offset into a deflated dataset, a whole-file finding, hostile text and file names, and omitted results. The tool exits 0 even when it reports problems, so the job reads its output and fails on any error or warning. Its first run found that notification descriptors lacked the `help` text its GitHub rules require of every descriptor (GH2012), now fixed. The remaining notes are declined on purpose: embedded file contents and snippets (SARIF2010, 2011, 2013) would copy malware and patient data into the log, and message arguments instead of text (SARIF2002) are rejected by GitHub (GH1007).
- **Hostile input:** file names that are not valid Unicode, bidirectional overrides, link and HTML syntax, and placeholders, each with a regression test.

## Using it in GitHub Actions

```yaml
permissions:
  contents: read
  security-events: write
steps:
  - uses: actions/checkout@v7
  - uses: actions/setup-python@v7
    with: {python-version: "3.13"}
  - run: pip install radguard
  # 1 means findings: let the upload run, and let code scanning decide what blocks a pull request.
  - run: radguard scan . --format sarif --output radguard.sarif || [ $? -eq 1 ]
  - uses: github/codeql-action/upload-sarif@v4
    with: {sarif_file: radguard.sarif, category: radguard}
```

Run RadGuard from the repository root: GitHub resolves relative URIs against it. Write the log with `--output` rather than shell redirection, because Windows PowerShell 5.1's `>` writes UTF-16, which SARIF consumers reject.

## Known limitations

- Regions mark where a finding starts, not its extent.
- GitHub cannot preview binary files, so an alert shows the file and offset but no snippet, and region-less alerts probably do not annotate pull request diffs.
- File names are part of the log by necessity. A DICOM archive whose file names contain patient identifiers should not be uploaded to a service that is not approved for patient data.
